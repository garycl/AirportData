# AirportData

Published BTS aviation data — aggregated airport-level parquets plus a handful of airport
reference and pricing tables. The heavy raw survey extracts are deliberately not here; this
repo carries only the small derived outputs that dashboards and forecast models actually read.

**Read [`METHODOLOGY.md`](./METHODOLOGY.md) first for anything analytical.** It is the
authoritative reference for sample fractions, the DB1B-to-OD40 survey break, fare and yield
contracts, carrier-field semantics, and the change history. This README does not repeat any of
it. This README is the orientation layer: what each file and directory is, who writes it, who
reads it, and on what schedule.

**This is a PUBLIC repo and it must stay public.** Its primary consumer is a browser-based
dashboard that reads these parquets directly with DuckDB-WASM over anonymous
`https://raw.githubusercontent.com/.../master/<path>` URLs — no server, no credentials, no
build step in between. Two consequences follow, and both are load-bearing:

1. **Do not make this repo private.** Every raw URL would start returning 404 and the airport
   dashboard would break instantly.
2. **Never enable Git LFS here.** `raw.githubusercontent.com` serves the LFS *pointer stub*
   (a ~130-byte text file) instead of the real object, so DuckDB-WASM and `pandas.read_parquet`
   would both fail on it. There is no `.gitattributes` in this repo today; keep it that way.
   Files too large for plain git belong in Dropbox, not in LFS — see the size rule in
   [`.gitignore`](./.gitignore).

## How the data is refreshed

The producing pipeline is **`dot-download`**
(`github.com/Unison-Consulting-Inc/dot-download`, **private** — org membership
required). Read `dot-download/RUNBOOK.md` before running anything by hand.

**Automated path — GitHub Actions `bts-refresh.yml`**
(`dot-download/.github/workflows/bts-refresh.yml`). The workflow checks out this repo with
`secrets.AIRPORTDATA_PUSH_TOKEN`, runs the pipeline with `--data-dir` pointed at that checkout
and `--no-push`, then does its own `git add -A` / commit / push:

| Cron (UTC) | Dataset | BTS publication window |
|---|---|---|
| `0 12 10 * *` | OD40 — `od40_pipeline.py` | ~10th of the month |
| `0 12 15 * *` | T-100 — `t100_download.py` | ~15th of the month |
| `0 12 20 * *` | Form 41 — `form41_download.py` | ~20th of the month |

The "Pick dataset by date" step accepts the scheduled day or one day late and fails loudly on
any other date rather than guessing. `workflow_dispatch` takes a `dataset` input
(`od40` / `t100` / `form41`) to force a specific run.

`airport_fuel.parquet` is on a separate weekly schedule owned by `util/fuel-price`
(`launchd/com.airport-fuel.weekly.plist`), which pushes directly to this repo.

**Legacy path — launchd on the maintainer's Mac.** `com.bts-data.od40.plist` (day 10, 06:00),
`com.bts-data.t100.plist` (day 15, 06:00), `com.bts-data.form41.plist` (day 20, 06:00). There
is deliberately **no** DB1B plist — see the survey-break caveat below.

**Manual run**, from a `dot-download` checkout with this repo cloned alongside:

```
python3 od40_pipeline.py   --no-push --data-dir ../AirportData   # current O&D
python3 t100_download.py   --no-push --data-dir ../AirportData
python3 form41_download.py --no-push --data-dir ../AirportData

# then, from this repo's checkout:
git add -A
git commit -m "data: <dataset> refresh <YYYY-MM> (manual fallback)"
git push
```

Verify by checking that `data_availability.json` advanced to the period you expected. Note that
`t100_download.py` and `form41_download.py` do **not** refresh `data_availability.json` — for
those, confirm the new parquet files under the dataset directory instead.

## Caveats

### METHODOLOGY.md is the authoritative analytical reference

Do not do fare, yield, passenger, or carrier analysis off this README.
[`METHODOLOGY.md`](./METHODOLOGY.md) carries the binding rules: sample fractions and reweighting
multipliers, the additive fare/yield component contracts (never average precomputed fares or
yields), which carrier field pairs with which across datasets, the NPIAS filtering order, and
the changelog including the 2026-04 `AvgMktFare` pax-weighting fix that invalidated every
pre-2026-04-17 downstream extract.

### The 2025 Q2 to Q3 survey break is real

BTS retired the quarterly DB1B survey after 2025 Q2 and replaced it with the monthly OD40
(DB1C) survey — a different sample fraction (10% vs 40%), different reporting rules, different
carrier coverage, different time grain. The DB1B-shaped files in `db1b_mkt/` and `db1b_tix/`
**blend both surveys across 2025** (Q1/Q2 legacy DB1B, Q3/Q4 OD40 rescaled to 10%-equivalent)
so dashboards see a continuous series. The break is still there. METHODOLOGY.md section
"Important: methodology break at 2025 Q2 to Q3" is required reading before any cross-2025
comparison.

Operationally this means: **do not run `db1b_download.py` for a current refresh.** It is
disabled by default and requires `--allow-legacy-db1b`. A pure DB1B rebuild can overwrite the
merged 2025 Q3+ OD40 rows and silently regress `data_availability.json` and every dashboard
back to 2025 Q2. After any bounded legacy backfill, rerun `od40_pipeline.py --no-push` and
require the merge validation to pass before committing.

### Raw per-period extracts are excluded by size

The raw DB1B per-quarter and OD40 per-month parquets are 100 MB to 1 GB each and are not in
this repo — see the size-based rules in `.gitignore` (`db1b_mkt/dbmkt_*_[1-4].parquet`,
`db1b_mkt/quarter/`, `db1b_tix/quarter/`, `od40/month/`, `*.csv`). They live only in the
maintainer's local Dropbox data directory.

This matters because **several consumers read those excluded files, not this repo**:
`unison/route-profit` reads `db1b_mkt/quarter/`, `db1b_tix/quarter/` and `od40/month/`, and
`traffic-forecasts/forecasts/stl-2026` and `mry-{2025,2026}` read `db1b_mkt/quarter/`. A
successor who clones this repo will *not* be able to run those projects. They need either the
Dropbox data directory or a re-download via `dot-download`.

### This repo was re-imported on 2026-08-05

History was intentionally not carried over. `git log` shows a single commit,
"Initial import: current aggregates as of 2026-08-05". Treat this repo as a current-state
snapshot: pre-2026-08-05 provenance lives in METHODOLOGY.md's changelog, not in git history.
There is no earlier commit to diff against or revert to.

### This repo is both the write and the read target

The `bts-refresh` GitHub Action (in `Unison-Consulting-Inc/dot-download`) pushes
refreshed aggregates here on its monthly crons, and every runtime consumer fetches
from this repo's raw URLs: `dash-airport` (`src/lib/duckdb.ts:68`, `src/utils/api.ts:1`
— the latter is hardcoded and ignores the `VITE_DATA_URL` override),
`fuel-price/config.py:19-20`, and `rental-car-cfc`. A push to `master` here is
immediately live in the dashboard on its next page load.

### `Airport_CFC.parquet` publishing is manual and undocumented in code

`util/rental-car-cfc/src/publish.py` builds the parquet into `$DROPBOX_ROOT/data/rental-car/`
and stops there — it says so explicitly at `src/publish.py:7-9`. Getting it into this repo
requires a human running a `gh api -X PUT ...` command that exists only in prose
(`rental-car-cfc/RUNBOOK.md:46`, `CLAUDE.md:136`), followed by manually bumping
`DATA_FILE_VERSION` in `dash/airport/src/lib/duckdb.ts:71` to bust the raw-URL cache. This is
the most fragile link in the chain.

Note also that the two runbooks contradict each other on how to handle this repo:
`dot-download/RUNBOOK.md:105` instructs you to `git clone` it, while
`rental-car-cfc/RUNBOOK.md:46` says **never** clone it (it is multi-gigabyte). Both are
defensible for their own workflow; be aware of the clone cost before following the former.

### Five files have no generator anywhere — preserve them

`ntad_airports.parquet`, `L_CITY_MARKET_ID.parquet`, `Report127_Compiled.parquet`,
`air_to_truck.parquet`, and `Intermodal_Freight_Facilities_Air-to-Truck.csv` are not
produced by any script. Nothing can rebuild them; keep backups outside git.

`NPIAS_Airports.parquet` **does** have a generator: `npias_build.py` in the
`dot-download` repo (added 2026-08-10; `--check` mode verifies a fresh build against
this published file; the FAA source workbook is committed beside it). It is read by
the dashboard, the fuel-price pipeline, the CFC pipeline, and the BTS pipeline itself
— if it is ever lost or corrupted, rebuild it with that script rather than restoring
by hand.

The last three (`Report127_Compiled.parquet`, `air_to_truck.parquet`, and the intermodal CSV)
have **zero readers and zero writers** in any known codebase — they are orphaned. Do not
delete them on that basis alone; an unrecoverable file with no known consumer is still
unrecoverable, and the consumer may simply be outside this codebase.

### The pipeline code is private

`dot-download`, `fuel-price`, and `rental-car-cfc` are **private** repos under
`Unison-Consulting-Inc` — refreshing this data requires org membership. If a link to
one of them 404s, your account is not in the org (a 404 on a private repo means "no
access", not "no repo").

### Two schedule gaps worth knowing

- `t100_download.py` and `form41_download.py` do not refresh `data_availability.json`; only the
  OD40 and DB1B paths call `update_availability.py`. A green T-100 run therefore will not move
  `generated_at`.
- `data_manifest.json` is written by four scripts and read by none.
